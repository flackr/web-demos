The Asynchronous Problem

JavaScript is strictly single-threaded, meaning it can only execute one piece of code at a time. If a long-running task—like fetching data from a server—were executed synchronously, it would block the main thread and freeze the entire webpage.

To keep the user interface responsive, browsers use asynchronous APIs. The browser handles the heavy network lifting in the background and eventually notifies your JavaScript code when the operation is complete.

For a long time, the only way to handle that notification was to pass a function—a callback. This worked for simple scripts, but created major headaches as applications grew more complex:

  • Callback Hell: Running asynchronous tasks in sequence required nesting callbacks inside callbacks, leading to the infamous "Pyramid of Doom."
  • Inversion of Control: You had to trust that the API you called would execute your callback at the right time, and exactly once.
  • Brittle Error Handling: Tracking failures required tedious error checks at every single nested step, making try/catch nearly useless.

Callback Hell (The Pyramid of Doom)

When you need to perform multiple asynchronous operations in a specific sequence, callbacks force you to nest each subsequent step inside the previous one's callback function.

This pattern causes code to grow horizontally rather than vertically. As the nesting deepens, the logic becomes incredibly difficult to read, track, and maintain.

Notice the error handling: you cannot use a single try/catch block. Instead, you are forced to manually check for and handle errors at every single level of the pyramid. 


getUser(userId, function(err, user) {
  if (err) return handleError(err);

  getPosts(user.id, function(err, posts) {
    if (err) return handleError(err);

    getComments(posts[0].id, function(err, comments) {
      if (err) return handleError(err);

      getAuthor(comments[0].authorId, function(err, author) {
        if (err) return handleError(err);

        console.log("Finally got the author:", author);
      });
    });
  });
});

Callbacks in the Wild: Browser APIs

Before Promises were standardized in ES6 (2015), the entire web platform was built around callbacks and event listeners.

Any operation that didn't finish immediately—like waiting for a timer, asking for user location, or interacting with a local database—required passing a function to be executed later.

This meant developers had to juggle constantly shifting conventions, as some APIs accepted callbacks as direct arguments, while others relied on attaching functions to event handlers.

Built-in Callback Examples

  • Timers (setTimeout / setInterval): The most fundamental examples of passing a callback function to be executed after a delay.
  • XMLHttpRequest: Handled asynchronous networking by attaching functions to properties like onload, onerror, and onreadystatechange.
  • Geolocation API: navigator.geolocation.getCurrentPosition() takes a success callback and an error callback as its first and second arguments.
  • IndexedDB: A complex local database API that relies entirely on request objects and firing onsuccess or onerror events.
  • WebRTC: Early versions of methods like RTCPeerConnection.createOffer() required passing success and failure callbacks (though they have since been modernized to support Promises).

Case Study: XMLHttpRequest

Using XMLHttpRequest required setting up event listeners for load and error states, which could quickly become nested and difficult to manage.

Introducing Promises

A Promise is an object representing the eventual completion (or failure) of an asynchronous operation, and its resulting value.

Instead of passing callbacks into an asynchronous function, the function returns a Promise object. You then attach your callbacks to that returned object.

This restores control to the developer. The Promise acts as a standard, reliable proxy for a value that is not necessarily known when the promise is created.

The Three States

At any given time, a Promise is in exactly one of these states:

  • Pending: The initial state. The operation has not completed yet.
  • Fulfilled: The operation completed successfully, yielding a value.
  • Rejected: The operation failed, yielding a reason (usually an Error object).

Once a promise transitions to Fulfilled or Rejected, it is considered settled. A settled promise is locked—its state and value can never change again, guaranteeing that your callbacks execute exactly once.

Creating and Consuming Promises

To create a Promise from scratch, use the new Promise() constructor. It takes an executor function with two arguments: resolve and reject.

You call resolve(value) when your async task succeeds, and reject(reason) if it fails. You can then attach .then() for success and .catch() for errors.

Under the Hood: Building a Promise

To understand how Promises work, we can build a basic version. At its core, a Promise is an object that manages a state and a list of callbacks. When resolve() is called, it triggers the callbacks registered via .then().

The Fetch API

The fetch() API provides a modern, Promise-based alternative to XMLHttpRequest. Instead of relying on event listeners, fetch() returns a promise that resolves with a Response object. This allows us to cleanly chain methods like .json() and handle errors in a single .catch() block.

Introducing Async / Await

Introduced in ES2017, async and await act as "syntactic sugar" on top of Promises. They don't replace Promises; they just make working with them much easier to read and write.

Marking a function as async ensures it always returns a Promise. Inside that function, you can use the await keyword to pause execution until a Promise settles, flattening out .then() chains into code that looks completely synchronous.

Case study: await fetch

The async and await keywords provide a cleaner, more readable syntax for working with Promises. By marking a function as async, you can use await to pause execution until a Promise resolves. This makes asynchronous code look and behave a bit more like synchronous code, allowing us to use standard try/catch blocks for error handling.

Unhandled Promise Rejections

What happens if a Promise rejects, but you forgot to attach a .catch() block (or didn't wrap your await in a try/catch)?

This is known as an unhandled rejection. Historically, these failed silently, making bugs incredibly hard to track down. Today, modern environments (both browsers and Node.js) treat them very seriously, printing loud warnings or even crashing the application.

In the browser, you can globally track these using the unhandledrejection window event. This acts as a safety net, allowing you to log unexpected errors to your server or monitoring service.

Concurrent Execution with Promise.all

When you have multiple asynchronous tasks that don't depend on each other, using await in a sequence can slow down your application because each task waits for the previous one to finish.

Promise.all() takes an array of promises and runs them concurrently. It returns a single Promise that resolves with an array of results only when all of the input promises have fulfilled. If even one promise rejects, the entire Promise.all() rejects immediately.

Promise.race vs Promise.any

Sometimes you want to react as soon as a single Promise finishes out of a group, rather than waiting for all of them.

  • Promise.race() settles as soon as the first promise settles, regardless of whether it fulfills or rejects.
  • Promise.any() settles as soon as the first promise is fulfilled. It completely ignores early rejections unless all promises in the array reject.

In this demo, we run two tasks: a fast one that fails (500ms) and a slower one that succeeds (1000ms). Notice how each method behaves!

Promise.allSettled

While Promise.all() fails fast (it rejects immediately if any promise rejects), there are times when you want to wait for all tasks to finish, regardless of whether they succeeded or failed.

Promise.allSettled() waits for all input promises to either fulfill or reject. It returns a single Promise that resolves to an array of objects, each describing the outcome of a promise. Each object has a status of either "fulfilled" or "rejected", along with the corresponding value or reason.

Summary: The Promise API

Core Concepts

Promises transformed JavaScript by providing a standard way to represent the eventual result of an asynchronous operation, rescuing us from Callback Hell.

  • Three States: pending, fulfilled (success), or rejected (error). Once settled, a Promise's state and value are permanently locked.
  • .then() and .catch(): The foundation for chaining sequential asynchronous operations and catching errors.
  • async / await: Modern syntax that lets you write asynchronous code that reads sequentially, making standard try/catch blocks viable again.

Combinators

Powerful tools for handling multiple promises simultaneously:

  • Promise.all(): All must succeed. Fails fast on the first error.
  • Promise.allSettled(): Waits for all to finish, capturing every success and failure.
  • Promise.race(): The first to settle wins (whether success or failure).
  • Promise.any(): The first to succeed wins. Ignores failures unless they all fail.
But wait... When exactly do these callbacks run? Now that we know how Promises work, it's time to look at the Event Loop, Macrotasks, and Microtasks!

Microtasks vs Macrotasks

Not all asynchronous callbacks are treated equally by the JavaScript Event Loop. They are divided into two main queues:

  • Macrotasks: Things like setTimeout, setInterval, and UI rendering.
  • Microtasks: Promise callbacks (.then, .catch, .finally) and queueMicrotask().

The Golden Rule: After the current synchronous code finishes, the engine will completely empty the Microtask queue before it moves on to the next Macrotask. This means Promise callbacks always jump ahead of setTimeout in line!

Microtask Checkpoints & Rendering

What happens when a Promise is resolved by the browser itself—like a fetch() completing or a Web Animation's .finished promise resolving? You didn't execute that code; the browser did.

The HTML specification defines explicit Microtask Checkpoints. The browser pauses to completely empty the microtask queue at specific, guaranteed moments. The most crucial checkpoints occur:

  • Immediately after any macrotask finishes (e.g., an event handler or a fetch network task).
  • During the "Update the Rendering" phase: specifically after requestAnimationFrame callbacks execute, but before the pixels are painted to the screen.

This design guarantees that if an animation finishes or data arrives and your Promise callback updates the DOM, the browser will wait for those changes and paint them in the very same frame, preventing flickering!

Summary: Promises and Timing

The Event Loop Hierarchy

Promises don't just run "later"—they run with a very specific priority dictated by the Microtask Queue.

  • Microtasks have priority: Promise callbacks (.then, .catch) are microtasks. They always run before the next macrotask (like setTimeout).
  • The Golden Rule: The JavaScript engine will completely empty the microtask queue before it allows any other asynchronous macrotask to execute.
  • Synchronous first: A Promise callback will never interrupt currently running synchronous code.

Browser Integration

The browser uses explicit Microtask Checkpoints to ensure Promises play nicely with the DOM and rendering pipeline:

  • Event Dispatching: When multiple native events fire (like mouseover then mouseenter), the browser hits a checkpoint between them. All Promise callbacks from the first event finish before the second event begins.
  • Rendering and Animation: A checkpoint occurs right after requestAnimationFrame callbacks but before the pixels hit the screen. This allows Promises to finalize DOM updates in the same frame, preventing visual flickering.
Key Takeaway: Promises give you deterministic, predictable control over asynchronous timing, seamlessly weaving your logic between user events and screen paints!
